What is a Unix timestamp?

Unix time counts the seconds that have passed since midnight UTC on 1 January 1970, a moment called the epoch. Because it is a single number with no time zone attached, it is how databases, log files, APIs and JWTs usually store “when”. The same instant is the same number in Dhaka, London and New York — only the way it is displayed changes.

Seconds, milliseconds or more?

Different systems use different precision. Unix tools, PHP and most APIs use seconds (10 digits today), JavaScript’s Date.now() and Java use milliseconds (13 digits), and some databases and Go use microseconds (16) or nanoseconds (19). This converter guesses the unit from the number of digits and tells you what it assumed; if the guess is wrong, choose the unit yourself. Negative values are dates before 1970.

Reading the results

  • ISO 8601 (2023-11-14T22:13:20.000Z) is the best format for storing and exchanging dates; the Z means UTC.
  • RFC 2822 is the style used in email headers, and the HTTP date appears in headers such as Last-Modified.
  • Asia/Dhaka is UTC+6 with no daylight saving time (Bangladesh briefly used UTC+7 in 2009, which the converter handles).

The Year 2038 problem

Old software stores Unix time in a signed 32-bit integer, whose largest value is 2,147,483,647 — 03:14:07 UTC on 19 January 2038. One second later such counters overflow to a date in 1901. Modern systems use 64-bit time, but embedded devices and old database columns may not. The converter warns when a value does not fit in 32 bits.

FAQ

Does Unix time include leap seconds?

No. Every Unix day is exactly 86,400 seconds, so leap seconds are simply not counted.

Why does my local time look wrong?

Local time comes from your device’s time zone setting. Check that it is correct, or compare with the UTC and Dhaka rows.

ইউনিক্স টাইমস্ট্যাম্প কী?

ইউনিক্স সময় হলো ১৯৭০ সালের ১ জানুয়ারি UTC মধ্যরাত থেকে এখন পর্যন্ত কত সেকেন্ড পেরিয়েছে তার হিসাব; ওই মুহূর্তকে বলা হয় epoch। এটি কোনো টাইম জোন ছাড়া একটি মাত্র সংখ্যা, তাই ডেটাবেস, লগ ফাইল, API আর JWT সাধারণত “কখন” এভাবেই রাখে। একই মুহূর্ত ঢাকা, লন্ডন বা নিউ ইয়র্কে একই সংখ্যা — শুধু দেখানোর ধরন বদলায়।

সেকেন্ড, মিলিসেকেন্ড নাকি আরও সূক্ষ্ম?

বিভিন্ন সিস্টেম বিভিন্ন সূক্ষ্মতা ব্যবহার করে। ইউনিক্স টুল, PHP ও বেশিরভাগ API সেকেন্ড ব্যবহার করে (এখন ১০ অঙ্ক), JavaScript-এর Date.now() ও Java মিলিসেকেন্ড (১৩ অঙ্ক), আর কিছু ডেটাবেস ও Go মাইক্রোসেকেন্ড (১৬) বা ন্যানোসেকেন্ড (১৯)। এই কনভার্টার অঙ্কের সংখ্যা দেখে একক অনুমান করে এবং কী ধরে নিয়েছে তা জানায়; অনুমান ভুল হলে নিজেই একক বেছে নিন। ঋণাত্মক মান মানে ১৯৭০-এর আগের তারিখ।

ফলাফল কীভাবে পড়বেন

  • ISO 8601 (2023-11-14T22:13:20.000Z) তারিখ সংরক্ষণ ও আদান-প্রদানের সবচেয়ে ভালো ফরম্যাট; শেষের Z মানে UTC।
  • RFC 2822 ইমেইল হেডারে ব্যবহৃত ধরন, আর HTTP date দেখা যায় Last-Modified-এর মতো হেডারে।
  • Asia/Dhaka হলো UTC+6, কোনো ডেলাইট সেভিং নেই (২০০৯ সালে বাংলাদেশ অল্প সময়ের জন্য UTC+7 ব্যবহার করেছিল, কনভার্টার সেটাও হিসাব করে)।

২০৩৮ সালের সমস্যা

পুরোনো সফটওয়্যার ইউনিক্স সময় সাইনড ৩২-বিট পূর্ণসংখ্যায় রাখে, যার সর্বোচ্চ মান ২,১৪৭,৪৮৩,৬৪৭ — ২০৩৮ সালের ১৯ জানুয়ারি UTC ০৩:১৪:০৭। এর এক সেকেন্ড পর এমন কাউন্টার উল্টে ১৯০১ সালের তারিখে চলে যায়। আধুনিক সিস্টেম ৬৪-বিট সময় ব্যবহার করে, কিন্তু এমবেডেড ডিভাইস বা পুরোনো ডেটাবেস কলাম হয়তো করে না। কোনো মান ৩২ বিটে না আঁটলে কনভার্টার সতর্ক করে।
