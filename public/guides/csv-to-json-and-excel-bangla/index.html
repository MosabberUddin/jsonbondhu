Convert CSV to JSON — and open Bangla CSV in Excel

Someone exports a customer list from an admin panel and sends it over. You need it as JSON for an API import — and your manager needs to open it in Excel. Two things go wrong again and again: the conversion quietly damages data (phone numbers lose their leading 0, a comma inside an address shifts every column), and Excel shows the Bangla names as à¦°à¦¹à¦¿à¦® instead of রহিম. This guide explains why both happen and how to fix them for good.

What a CSV file really is

CSV (“comma-separated values”) looks too simple to need rules, which is exactly why people get it wrong. The closest thing to a standard is RFC 4180:

  • One record per line; lines end with CRLF (\r\n), though most readers also accept \n.
  • Fields are separated by commas. The first line is often, but not always, a header with column names.
  • A field that contains a comma, a double quote or a line break must be wrapped in double quotes.
  • A double quote inside a quoted field is written twice: "".
name,phone,note,address
"Uddin, Rahim",01712345678,"He said ""call after 5pm""","House 12, Road 5
Dhanmondi, Dhaka"
Karim,01812345678,,Sylhet

That file has two records, not three: the second line break is inside a quoted address. This is why you must never parse CSV with split(','):

'"Uddin, Rahim",01712345678'.split(',')
// [ '"Uddin', ' Rahim"', '01712345678' ]   ✗ three fields instead of two

Use a real parser: Python’s built-in csv module, a library such as Papa Parse in JavaScript, or a converter that follows the quoting rules.

Not every “CSV” uses commas

In countries where the decimal separator is a comma (much of Europe, for example), Excel saves “CSV” with semicolons, because 1250,50 would otherwise be split in two. You will also meet tab-separated files (TSV) and pipes (|). Check the first line before converting, or use a tool that detects the delimiter.

Headers become keys

When converting to JSON, each header becomes a key and each row becomes an object. Clean headers make clean JSON: Customer Name works as a key but is awkward to use in code; customer_name is easier. Watch for empty and duplicate header cells — two columns named phone cannot both be keys of one object, so a converter has to rename one or lose data.

The type-guessing trap

CSV has no types; every cell is text. A converter that “helpfully” turns numeric-looking text into numbers can destroy data:

Cell textNaive conversionWhat went wrong
017123456781712345678Mobile number lost its leading 0
1250.501250.5Formatting of an amount changed
0012 (product code)12Different code
১২৩ (Bangla digits)NaNNumber() only understands 0–9

Rule of thumb: identifiers are text, even when they look like numbers — phone numbers, NID and account numbers, postcodes, invoice numbers. Only convert columns you will actually calculate with. Excel has the same problem when it opens a CSV: it strips leading zeros and keeps only 15 significant digits, so long ID numbers can be permanently changed if you save the file again.

How JSON Bondhu handles it: with “Detect numbers, true/false, null” on, a cell only becomes a number if it converts back to exactly the same text. 980 becomes 980, but 01712345678 and 1250.50 stay strings.

Nested data: dot keys and flattening

JSON can nest; CSV is flat. The usual bridge is dot notation in the headers:

id,customer.name,customer.city
1,রহিম,Dhaka

→ [ { "id": 1, "customer": { "name": "রহিম", "city": "Dhaka" } } ]

Going the other way, JSON → CSV flattens nested objects into dot keys. Arrays have no natural place in a table, so they are usually written as JSON text inside one cell (note the doubled quotes):

[{ "id": 1, "customer": { "name": "রহিম", "city": "Dhaka" }, "tags": ["new", "cod"] }]

→ id,customer.name,customer.city,tags
  1,রহিম,Dhaka,"[""new"",""cod""]"

If different objects have different keys, the CSV gets the union of all columns and missing values become empty cells.

Why Excel breaks Bangla text

Bangla characters take three bytes each in UTF-8. When you double-click a CSV, Excel on Windows usually has no way to know the file is UTF-8, so it reads the bytes with the system’s legacy code page (typically Windows-1252). Each Bangla letter becomes three Latin characters, and রহিম turns into à¦°à¦¹à¦¿à¦®. The file itself is fine — only the reading is wrong. There are three reliable fixes.

Fix 1: save the CSV with a UTF-8 BOM

A byte-order mark is three bytes (EF BB BF) at the very start of the file. Excel sees them and reads the file as UTF-8. When you generate CSV for Excel users, add it:

// Node.js
import { writeFileSync } from 'node:fs';
const csv = 'name,phone,city\r\nরহিম,01712345678,ঢাকা\r\n';
writeFileSync('customers.csv', '﻿' + csv, 'utf8');

# Python: "utf-8-sig" writes the BOM (and strips it when reading)
import csv
with open("customers.csv", "w", encoding="utf-8-sig", newline="") as f:
    csv.writer(f).writerows([["name", "phone"], ["রহিম", "01712345678"]])

# pandas
df.to_csv("customers.csv", index=False, encoding="utf-8-sig")

Fix 2: import instead of double-clicking

For a file you received without a BOM: open a blank workbook, go to Data → From Text/CSV, pick the file, set File Origin to 65001: Unicode (UTF-8) and check that the delimiter is right. The preview should show proper Bangla; then click Load. You can also set the phone column to Text here so the leading zeros survive.

Fix 3: save from Excel as “CSV UTF-8”

When you save a sheet containing Bangla, choose CSV UTF-8 (Comma delimited), not plain “CSV (Comma delimited)”. The plain option uses the legacy code page and Bangla characters come out as question marks.

Google Sheets has none of these problems: File → Import reads UTF-8 correctly, and its CSV download is UTF-8.

The BOM cuts both ways. Programs that don’t expect it may read the first header as "﻿name" instead of "name", so row.name is undefined. When reading CSV in code, strip it: encoding="utf-8-sig" in Python, or text.replace(/^﻿/, '') in JavaScript.

A complete CSV → JSON script in Python

import csv, json

with open("orders.csv", encoding="utf-8-sig", newline="") as f:
    rows = list(csv.DictReader(f))   # every value stays a string, so 017… is safe

with open("orders.json", "w", encoding="utf-8") as f:
    json.dump(rows, f, ensure_ascii=False, indent=2)

newline="" lets the csv module handle line breaks inside quoted fields, and ensure_ascii=False keeps Bangla readable in the output instead of র escapes.

One security note: CSV injection

If a CSV you export contains user-supplied text starting with =, +, - or @, Excel or Google Sheets may treat it as a formula when the file is opened. A common defence is to prefix such cells with an apostrophe so they display as plain text — only do this for files meant for spreadsheets, since it changes the value.

FAQ

I added a BOM but Excel still shows everything in one column. Why?

That is a delimiter problem, not an encoding one. Your Excel probably expects semicolons because of regional settings. Use Data → From Text/CSV and choose the delimiter manually, or export with semicolons for those users.

How do I keep leading zeros when opening a CSV in Excel?

Import it with Data → From Text/CSV and set that column’s type to Text before loading. Double-clicking the file lets Excel guess, and it will turn 01712345678 into a number.

Should empty cells become null or an empty string?

It depends on the receiving system. null usually means “unknown”, "" means “known to be empty”. Pick one rule per column and document it; for numeric columns null is almost always right.

CSV থেকে JSON — আর এক্সেলে বাংলা CSV ঠিকমতো খোলা

কেউ অ্যাডমিন প্যানেল থেকে কাস্টমারের লিস্ট এক্সপোর্ট করে পাঠালেন। API-তে ইমপোর্ট করতে আপনার দরকার JSON — আর আপনার ম্যানেজার ফাইলটা খুলবেন এক্সেলে। এখানে দুটো সমস্যা বারবার ঘটে: কনভার্ট করার সময় ডেটা নিঃশব্দে নষ্ট হয় (ফোন নম্বরের শুরুর 0 হারিয়ে যায়, ঠিকানার ভেতরের একটা কমা সব কলাম এক ঘর সরিয়ে দেয়), আর এক্সেলে বাংলা নাম রহিম-এর বদলে দেখায় à¦°à¦¹à¦¿à¦®। কেন এমন হয় আর কীভাবে স্থায়ীভাবে ঠিক করবেন — এই গাইডে সেটাই।

CSV ফাইল আসলে কী

CSV (“comma-separated values”) দেখতে এতই সহজ যে মনে হয় কোনো নিয়ম লাগে না — আর ঠিক এ কারণেই মানুষ ভুল করে। স্ট্যান্ডার্ড বলতে সবচেয়ে কাছের জিনিস হলো RFC 4180:

  • প্রতি লাইনে একটি রেকর্ড; লাইন শেষ হয় CRLF (\r\n) দিয়ে, যদিও বেশিরভাগ রিডার \n-ও মেনে নেয়।
  • ফিল্ডগুলো কমা দিয়ে আলাদা। প্রথম লাইন প্রায়ই (তবে সবসময় নয়) কলামের নামসহ হেডার।
  • যে ফিল্ডে কমা, ডাবল কোট বা লাইন-ব্রেক আছে, সেটা অবশ্যই ডাবল কোটে মুড়তে হবে।
  • কোটের ভেতরের ফিল্ডে ডাবল কোট লিখতে হয় দুবার: ""।
name,phone,note,address
"Uddin, Rahim",01712345678,"He said ""call after 5pm""","House 12, Road 5
Dhanmondi, Dhaka"
Karim,01812345678,,Sylhet

এই ফাইলে রেকর্ড দুটি, তিনটি নয়: দ্বিতীয় লাইন-ব্রেকটা কোটের ভেতরের ঠিকানার অংশ। এ কারণেই কখনো split(',') দিয়ে CSV পার্স করবেন না:

'"Uddin, Rahim",01712345678'.split(',')
// [ '"Uddin', ' Rahim"', '01712345678' ]   ✗ দুটির বদলে তিনটি ফিল্ড

আসল পার্সার ব্যবহার করুন: Python-এর বিল্ট-ইন csv মডিউল, JavaScript-এ Papa Parse-এর মতো লাইব্রেরি, অথবা কোটের নিয়ম মেনে চলে এমন কোনো কনভার্টার।

সব “CSV”-তে কমা থাকে না

যেসব দেশে দশমিক চিহ্ন হিসেবে কমা ব্যবহার হয় (যেমন ইউরোপের অনেক দেশ), সেখানে এক্সেল “CSV” সেভ করে সেমিকোলন দিয়ে, কারণ নইলে 1250,50 দুই ভাগ হয়ে যেত। ট্যাব দিয়ে আলাদা করা ফাইল (TSV) আর পাইপ (|)-ও দেখবেন। কনভার্ট করার আগে প্রথম লাইনটা দেখে নিন, অথবা এমন টুল ব্যবহার করুন যা ডিলিমিটার নিজেই চিনে নেয়।

হেডার হয়ে যায় কী

JSON-এ রূপান্তরের সময় প্রতিটি হেডার হয় একটি কী, আর প্রতিটি সারি হয় একটি অবজেক্ট। হেডার পরিষ্কার হলে JSON-ও পরিষ্কার: Customer Name কী হিসেবে চলে, কিন্তু কোডে ব্যবহার করা ঝামেলার; customer_name অনেক সহজ। ফাঁকা বা একই নামের হেডার সম্পর্কে সতর্ক থাকুন — phone নামের দুটি কলাম একই অবজেক্টের দুটি কী হতে পারে না, তাই কনভার্টারকে হয় একটির নাম বদলাতে হবে, নয়তো ডেটা হারাবে।

টাইপ অনুমানের ফাঁদ

CSV-তে কোনো টাইপ নেই; প্রতিটি ঘরই লেখা। যে কনভার্টার “উপকার করতে গিয়ে” সংখ্যার মতো দেখতে লেখাকে সংখ্যা বানিয়ে দেয়, সে ডেটা নষ্ট করতে পারে:

ঘরের লেখাঅসতর্ক রূপান্তরকী ভুল হলো
017123456781712345678মোবাইল নম্বরের শুরুর 0 হারিয়ে গেল
1250.501250.5টাকার অঙ্কের ফরম্যাট বদলে গেল
0012 (প্রোডাক্ট কোড)12অন্য কোড হয়ে গেল
১২৩ (বাংলা অঙ্ক)NaNNumber() শুধু 0–9 বোঝে

মূল নিয়ম: পরিচয়সূচক জিনিস সবসময় লেখা, দেখতে সংখ্যার মতো হলেও — ফোন নম্বর, NID ও অ্যাকাউন্ট নম্বর, পোস্টকোড, ইনভয়েস নম্বর। শুধু সেই কলামগুলো সংখ্যায় রূপান্তর করুন, যেগুলো দিয়ে সত্যিই হিসাব করবেন। CSV খোলার সময় এক্সেলেরও একই সমস্যা: শুরুর শূন্য ফেলে দেয় আর মাত্র ১৫টি significant digit রাখে, ফলে ফাইলটা আবার সেভ করলে লম্বা আইডি নম্বর স্থায়ীভাবে বদলে যেতে পারে।

JSON বন্ধু যেভাবে সামলায়: “সংখ্যা, true/false, null চিনে নিন” চালু থাকলে একটি ঘর তখনই সংখ্যা হয়, যখন সেটা আবার হুবহু একই লেখায় ফেরত যায়। 980 হয় 980, কিন্তু 01712345678 আর 1250.50 স্ট্রিংই থাকে।

নেস্টেড ডেটা: ডট কী আর ফ্ল্যাটেনিং

JSON-এ নেস্টিং চলে; CSV সমতল। দুটির মধ্যে সেতু সাধারণত হেডারে ডট নোটেশন:

id,customer.name,customer.city
1,রহিম,Dhaka

→ [ { "id": 1, "customer": { "name": "রহিম", "city": "Dhaka" } } ]

উল্টো দিকে, JSON → CSV করার সময় নেস্টেড অবজেক্ট ফ্ল্যাটেন হয়ে ডট কী হয়ে যায়। টেবিলে অ্যারের কোনো স্বাভাবিক জায়গা নেই, তাই সাধারণত সেগুলো এক ঘরের ভেতরে JSON লেখা হিসেবে বসানো হয় (দ্বিগুণ কোট খেয়াল করুন):

[{ "id": 1, "customer": { "name": "রহিম", "city": "Dhaka" }, "tags": ["new", "cod"] }]

→ id,customer.name,customer.city,tags
  1,রহিম,Dhaka,"[""new"",""cod""]"

আলাদা অবজেক্টে আলাদা কী থাকলে CSV-তে সব কলামের মিলিত তালিকা আসে, আর যেখানে মান নেই সেখানে ঘর ফাঁকা থাকে।

এক্সেল কেন বাংলা লেখা ভেঙে ফেলে

UTF-8-এ প্রতিটি বাংলা অক্ষর তিন বাইট জায়গা নেয়। CSV-তে ডাবল-ক্লিক করলে Windows-এর এক্সেল সাধারণত বুঝতে পারে না ফাইলটা UTF-8, তাই সিস্টেমের পুরোনো code page (সাধারণত Windows-1252) দিয়ে বাইটগুলো পড়ে। ফলে প্রতিটি বাংলা অক্ষর হয়ে যায় তিনটি ল্যাটিন অক্ষর, আর রহিম হয়ে যায় à¦°à¦¹à¦¿à¦®। ফাইলে কোনো সমস্যা নেই — ভুলটা শুধু পড়ায়। ঠিক করার তিনটি নির্ভরযোগ্য উপায় আছে।

উপায় ১: UTF-8 BOM দিয়ে CSV সেভ করুন

Byte-order mark হলো ফাইলের একেবারে শুরুতে তিনটি বাইট (EF BB BF)। এগুলো দেখলে এক্সেল ফাইলটা UTF-8 হিসেবে পড়ে। এক্সেল ব্যবহারকারীদের জন্য CSV বানালে এটা যোগ করুন:

// Node.js
import { writeFileSync } from 'node:fs';
const csv = 'name,phone,city\r\nরহিম,01712345678,ঢাকা\r\n';
writeFileSync('customers.csv', '﻿' + csv, 'utf8');

# Python: "utf-8-sig" BOM লেখে (আর পড়ার সময় বাদ দেয়)
import csv
with open("customers.csv", "w", encoding="utf-8-sig", newline="") as f:
    csv.writer(f).writerows([["name", "phone"], ["রহিম", "01712345678"]])

# pandas
df.to_csv("customers.csv", index=False, encoding="utf-8-sig")

উপায় ২: ডাবল-ক্লিক না করে ইমপোর্ট করুন

BOM ছাড়া যে ফাইল আপনার হাতে এসেছে, তার জন্য: একটি ফাঁকা workbook খুলে Data → From Text/CSV-এ যান, ফাইলটা বেছে নিন, File Origin-এ দিন 65001: Unicode (UTF-8), আর ডিলিমিটার ঠিক আছে কি না দেখুন। প্রিভিউতে বাংলা ঠিকঠাক দেখালে Load চাপুন। চাইলে এখানেই ফোন নম্বরের কলামকে Text করে দিতে পারেন, যাতে শুরুর শূন্য থেকে যায়।

উপায় ৩: এক্সেল থেকে “CSV UTF-8” হিসেবে সেভ করুন

বাংলা লেখাসহ শিট সেভ করার সময় সাধারণ “CSV (Comma delimited)” নয়, বেছে নিন CSV UTF-8 (Comma delimited)। সাধারণ অপশনটি পুরোনো code page ব্যবহার করে, ফলে বাংলা অক্ষরগুলো প্রশ্নবোধক চিহ্ন হয়ে যায়।

Google Sheets-এ এসব সমস্যা নেই: File → Import ঠিকভাবেই UTF-8 পড়ে, আর এর CSV ডাউনলোডও UTF-8।

BOM-এর উল্টো দিকও আছে। যে প্রোগ্রাম এটা আশা করে না, সে প্রথম হেডারকে "name"-এর বদলে পড়তে পারে "﻿name", ফলে row.name হয় undefined। কোডে CSV পড়ার সময় এটা বাদ দিন: Python-এ encoding="utf-8-sig", JavaScript-এ text.replace(/^﻿/, '')।

Python-এ পূর্ণাঙ্গ CSV → JSON স্ক্রিপ্ট

import csv, json

with open("orders.csv", encoding="utf-8-sig", newline="") as f:
    rows = list(csv.DictReader(f))   # প্রতিটি মান স্ট্রিং থাকে, তাই 017… নিরাপদ

with open("orders.json", "w", encoding="utf-8") as f:
    json.dump(rows, f, ensure_ascii=False, indent=2)

newline="" দিলে কোটের ভেতরের লাইন-ব্রেক csv মডিউল নিজেই সামলায়, আর ensure_ascii=False দিলে আউটপুটে বাংলা র-এর মতো এসকেপ না হয়ে পড়ার উপযোগী থাকে।

একটি নিরাপত্তা নোট: CSV ইনজেকশন

আপনার এক্সপোর্ট করা CSV-তে যদি ব্যবহারকারীর দেওয়া এমন লেখা থাকে যা =, +, - বা @ দিয়ে শুরু, তাহলে ফাইল খোলার সময় Excel বা Google Sheets সেটাকে ফর্মুলা হিসেবে ধরতে পারে। প্রচলিত প্রতিরোধ হলো এমন ঘরের শুরুতে একটি অ্যাপোস্ট্রফি (') বসানো, যাতে সেটা সাধারণ লেখা হিসেবে দেখায় — তবে এতে মান বদলে যায়, তাই শুধু স্প্রেডশিটের জন্য বানানো ফাইলে এটা করুন।

দুই দিকেই রূপান্তর, বাংলা নিরাপদে। CSV ↔ JSON কনভার্টার ডিলিমিটার নিজেই চেনে, ফোন নম্বর লেখা হিসেবে রাখে, আর এর CSV ডাউনলোডে UTF-8 BOM থাকে, তাই এক্সেলে বাংলা ঠিকঠাক দেখায়। এখনই চেষ্টা করুন

প্রশ্নোত্তর

BOM যোগ করেছি, তবু এক্সেলে সবকিছু এক কলামে দেখাচ্ছে। কেন?

এটা এনকোডিং নয়, ডিলিমিটারের সমস্যা। রিজিওনাল সেটিংসের কারণে আপনার এক্সেল সম্ভবত সেমিকোলন আশা করছে। Data → From Text/CSV দিয়ে হাতে ডিলিমিটার বেছে নিন, অথবা ওই ব্যবহারকারীদের জন্য সেমিকোলন দিয়ে এক্সপোর্ট করুন।

এক্সেলে CSV খোলার সময় শুরুর শূন্য কীভাবে রাখব?

Data → From Text/CSV দিয়ে ইমপোর্ট করুন, আর Load করার আগে ওই কলামের টাইপ Text করে দিন। ফাইলে ডাবল-ক্লিক করলে এক্সেল নিজে অনুমান করে, আর 01712345678-কে সংখ্যা বানিয়ে ফেলে।

ফাঁকা ঘর null হবে, না ফাঁকা স্ট্রিং?

যে সিস্টেম ডেটা নেবে তার ওপর নির্ভর করে। null সাধারণত বোঝায় “জানা নেই”, আর "" বোঝায় “জানা আছে যে ফাঁকা”। প্রতিটি কলামের জন্য একটা নিয়ম ঠিক করে লিখে রাখুন; সংখ্যার কলামে প্রায় সবসময় null-ই ঠিক।
