8 JWT security mistakes developers still make

JSON Web Tokens are not insecure by design, but they give you a lot of rope. The specification leaves many decisions to you — which algorithms to accept, how long tokens live, where the browser keeps them — and most real-world JWT vulnerabilities come from getting one of those decisions wrong. Here are eight mistakes that still show up in code reviews and bug-bounty reports, why each one matters, and what to do instead. If you are new to the format, start with how to decode a JWT.

1. Accepting alg: "none"

The JWT standard defines an “unsecured” token whose header says {"alg":"none"} and whose signature is empty. Some early libraries honoured that header, so an attacker could take any token, set the algorithm to none, edit the payload and delete the signature:

eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.<edited payload>.
// header = {"alg":"none","typ":"JWT"}, note the empty last part

Fix: never let the token choose its own algorithm. Configure the verifier with an explicit allow-list and reject everything else. Current versions of mainstream libraries reject none by default, but only if you don’t turn it back on or roll your own parser.

// JavaScript (jose)
await jwtVerify(token, key, { algorithms: ['RS256'], issuer, audience });

# Python (PyJWT)
jwt.decode(token, key, algorithms=["RS256"], audience=AUD, issuer=ISS)

2. Algorithm confusion (RS256 key used as an HS256 secret)

Your API expects RS256 tokens and verifies them with the provider’s public key — which, being public, the attacker also has. If the verification call is generic (“verify this token with this key”) and the library trusts the header’s alg, the attacker can send a token marked HS256 and sign it with HMAC, using the public key’s PEM text as the “secret”. The server runs HMAC with the same bytes and the signature matches.

Fix: pin the algorithm (see mistake 1), and keep keys typed: an RSA or EC public key should only ever be passed to an RSA or ECDSA verifier. Modern libraries refuse to use a PEM public key as an HMAC secret, which is another reason to keep them updated.

3. Weak or guessable HMAC secrets

With HS256 the whole security of every token rests on one secret. An attacker who has a single valid token can try billions of guesses per second offline — password-cracking tools have a JWT mode built in — without ever touching your server. Secrets like secret, changeme, the app name, or the example value from a tutorial fall in minutes.

Fix: use at least 256 bits of randomness (RFC 7518 requires a key at least as long as the hash output), keep it in a secret manager or environment variable, not in Git, and rotate it if it leaks.

node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
python -c "import secrets; print(secrets.token_urlsafe(32))"

If several independent services need to verify tokens, switch to RS256 or ES256 so that only the issuer holds a signing key.

4. Verifying the signature but not the claims

A valid signature only proves who issued the token. It does not prove the token is still valid or meant for you. Skipping exp means stolen tokens work forever; skipping nbf accepts tokens before their start time; skipping aud lets a token issued for your billing service be replayed against your admin API; skipping iss may accept tokens from a different tenant of the same identity provider.

Fix: pass the expected issuer and audience to the library and make exp required. Allow a small clock skew (30–60 seconds), not hours.

5. Putting sensitive data in the payload

A signed JWT is encoded, not encrypted. Anyone who sees it — the browser, a proxy, a log file, an analytics script — can read every claim. We regularly see national ID numbers, phone numbers, internal pricing flags and even password hashes in payloads.

Fix: keep the payload to what the receiving API needs to make a decision: a user ID, roles or scopes, expiry. Look everything else up on the server. If a token genuinely must carry confidential data, use encrypted JWE instead of a plain signed JWT.

6. Long-lived tokens with no way to revoke them

A JWT is valid until exp, even after the user logs out, changes their password or is banned — the server doesn’t look anything up. A 30-day access token is therefore a 30-day skeleton key if it leaks.

Fix: keep access tokens short (often 5–15 minutes) and pair them with a refresh token that is stored server-side, rotated on every use and revoked on logout. Reuse of an already-rotated refresh token is a strong signal of theft; revoke the whole family. For immediate revocation of access tokens, keep a small deny-list of jti values or a per-user “token version” until their natural expiry.

7. Storing tokens where XSS can read them

Tokens in localStorage or sessionStorage are readable by any JavaScript on the page. One cross-site scripting bug, or one compromised npm package or third-party script, can copy the token to an attacker’s server, where it keeps working until it expires.

An HttpOnly cookie can’t be read by JavaScript at all:

Set-Cookie: session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=900

This is not a free win, and it’s worth being honest about the trade-off:

localStorage + headerHttpOnly cookie
XSS can steal the tokenYesNo (but XSS can still make requests as the user while the page is open)
CSRF riskNone — the browser never attaches it automaticallyYes — the browser sends it automatically; mitigate with SameSite and CSRF tokens for state-changing requests
Works across domainsEasyNeeds careful CORS and cookie settings

Fix: for browser apps, prefer HttpOnly; Secure; SameSite cookies (or a backend-for-frontend that keeps tokens server-side entirely), add CSRF protection, and treat XSS prevention — output escaping and a Content Security Policy — as the real defence either way.

8. Pasting production tokens into online tools that upload them

A live access token is a credential. Many “JWT decoder” websites send what you paste to their server, where it may be logged, cached or analysed. If that token hasn’t expired, whoever reads those logs can call your API as that user.

Fix: debug with test tokens where possible; use tools that run entirely in your browser (you can confirm in the browser’s Network tab that nothing is sent); and if a real token was exposed, revoke the session or wait for it to expire rather than assuming nobody saw it.

Rule of thumb: the verifier decides the algorithm, the key and the expected claims. The token only brings data to be checked against those expectations.

FAQ

Are JWTs less secure than traditional sessions?

Not inherently. Server-side sessions are simpler to revoke and harder to misconfigure, so for a single web app they are often the better default. JWTs shine when several services must verify identity without a shared session store. Either way, the mistakes above are what make the difference.

Is HS256 unsafe? Should I always use RS256?

HS256 with a long random secret is secure. Its limitation is that every verifier can also sign. Use RS256 or ES256 when the verifiers are separate services or third parties; ES256 gives much shorter signatures.

Does HttpOnly protect me from XSS completely?

No. It stops a script from reading the token, but a script running in your page can still send requests that the browser authenticates with the cookie. It limits the damage to the time the page is open; it does not replace fixing XSS.

What should I do if a token leaked?

Revoke the related session or refresh token, add the jti to a deny-list if you have one, and if the signing secret itself may have leaked, rotate it — which invalidates every token signed with it.

JWT নিয়ে ৮টি নিরাপত্তা-ভুল যা ডেভেলপাররা এখনো করেন

JSON Web Token নিজে থেকে অনিরাপদ নয়, তবে এটা আপনাকে অনেক স্বাধীনতা দেয় — আর সেখানেই বিপদ। কোন অ্যালগরিদম গ্রহণ করবেন, টোকেন কতক্ষণ বৈধ থাকবে, ব্রাউজার কোথায় রাখবে — এমন অনেক সিদ্ধান্ত স্পেসিফিকেশন আপনার ওপর ছেড়ে দেয়, আর বাস্তবের বেশিরভাগ JWT দুর্বলতা আসে এর কোনো একটা ভুল করার ফলে। নিচে এমন আটটি ভুল দেওয়া হলো যা এখনো কোড রিভিউ আর bug-bounty রিপোর্টে দেখা যায় — কেন সমস্যা, আর বদলে কী করবেন। ফরম্যাটটা নতুন হলে আগে পড়ুন JWT কীভাবে ডিকোড করবেন।

১. alg: "none" গ্রহণ করা

JWT স্ট্যান্ডার্ডে একটা “unsecured” টোকেনের ধারণা আছে, যার হেডারে থাকে {"alg":"none"} আর সিগনেচার ফাঁকা। শুরুর দিকের কিছু লাইব্রেরি এই হেডার মেনে নিত, ফলে অ্যাটাকার যেকোনো টোকেন নিয়ে অ্যালগরিদম none করে, পেলোড বদলে, সিগনেচার মুছে পাঠিয়ে দিতে পারত:

eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.<edited payload>.
// header = {"alg":"none","typ":"JWT"}, শেষের অংশটা ফাঁকা

সমাধান: টোকেনকে কখনো নিজের অ্যালগরিদম নিজে বেছে নিতে দেবেন না। ভেরিফায়ারে অনুমোদিত অ্যালগরিদমের স্পষ্ট তালিকা দিন, বাকি সব বাতিল করুন। জনপ্রিয় লাইব্রেরির বর্তমান সংস্করণগুলো ডিফল্টভাবেই none বাতিল করে — যদি না আপনি নিজে আবার চালু করেন বা নিজের পার্সার লেখেন।

// JavaScript (jose)
await jwtVerify(token, key, { algorithms: ['RS256'], issuer, audience });

# Python (PyJWT)
jwt.decode(token, key, algorithms=["RS256"], audience=AUD, issuer=ISS)

২. অ্যালগরিদম কনফিউশন (RS256-এর কী HS256-এর সিক্রেট হিসেবে)

আপনার API RS256 টোকেন আশা করে এবং প্রোভাইডারের পাবলিক কী দিয়ে যাচাই করে — আর পাবলিক বলেই কী-টা অ্যাটাকারের হাতেও আছে। যাচাইয়ের কল যদি সাধারণ হয় (“এই কী দিয়ে এই টোকেন যাচাই করো”) আর লাইব্রেরি হেডারের alg-কে বিশ্বাস করে, তাহলে অ্যাটাকার HS256 লেখা একটা টোকেন পাঠাতে পারে, যেটা সে HMAC দিয়ে সাইন করেছে পাবলিক কী-এর PEM লেখাকে “সিক্রেট” বানিয়ে। সার্ভারও একই বাইট দিয়ে HMAC চালায়, আর সিগনেচার মিলে যায়।

সমাধান: অ্যালগরিদম নির্দিষ্ট করে দিন (১ নম্বর দেখুন), আর কী-এর ধরন আলাদা রাখুন: RSA বা EC পাবলিক কী শুধু RSA বা ECDSA ভেরিফায়ারেই যাবে। আধুনিক লাইব্রেরিগুলো PEM পাবলিক কী-কে HMAC সিক্রেট হিসেবে ব্যবহার করতে দেয় না — লাইব্রেরি আপডেট রাখার এটাও একটা কারণ।

৩. দুর্বল বা অনুমানযোগ্য HMAC সিক্রেট

HS256-এ সব টোকেনের পুরো নিরাপত্তা একটা সিক্রেটের ওপর দাঁড়িয়ে। যার হাতে একটা বৈধ টোকেন আছে, সে আপনার সার্ভারে না গিয়েই অফলাইনে প্রতি সেকেন্ডে কোটি কোটি অনুমান চালাতে পারে — পাসওয়ার্ড-ক্র্যাকিং টুলে JWT-এর জন্য আলাদা মোডই আছে। secret, changeme, অ্যাপের নাম বা কোনো টিউটোরিয়ালের উদাহরণ-মানের মতো সিক্রেট কয়েক মিনিটেই ভেঙে যায়।

সমাধান: অন্তত ২৫৬ বিট র‍্যান্ডম মান ব্যবহার করুন (RFC 7518 অনুযায়ী কী অন্তত হ্যাশ আউটপুটের সমান লম্বা হতে হবে), এটা Git-এ নয়, secret manager বা environment variable-এ রাখুন, আর ফাঁস হলে বদলে ফেলুন।

node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
python -c "import secrets; print(secrets.token_urlsafe(32))"

একাধিক আলাদা সার্ভিসকে টোকেন যাচাই করতে হলে RS256 বা ES256-এ চলে যান, যাতে সাইন করার কী শুধু ইস্যুকারীর কাছেই থাকে।

৪. সিগনেচার যাচাই করা, কিন্তু ক্লেইম না দেখা

বৈধ সিগনেচার শুধু প্রমাণ করে টোকেনটা কে ইস্যু করেছে। টোকেনটা এখনো বৈধ কি না বা আপনার জন্যই কি না, তা প্রমাণ করে না। exp না দেখলে চুরি হওয়া টোকেন চিরকাল চলবে; nbf না দেখলে শুরুর সময়ের আগেই টোকেন চলবে; aud না দেখলে আপনার বিলিং সার্ভিসের জন্য দেওয়া টোকেন অ্যাডমিন API-তে চালানো যাবে; iss না দেখলে একই আইডেন্টিটি প্রোভাইডারের অন্য কোনো tenant-এর টোকেনও গৃহীত হতে পারে।

সমাধান: লাইব্রেরিকে প্রত্যাশিত issuer ও audience দিয়ে দিন, আর exp বাধ্যতামূলক করুন। ঘড়ির অমিলের জন্য ৩০–৬০ সেকেন্ড ছাড় দিন, ঘণ্টার পর ঘণ্টা নয়।

৫. পেলোডে সংবেদনশীল তথ্য রাখা

সাইন করা JWT এনকোড করা, এনক্রিপ্ট করা নয়। যে-ই এটা দেখে — ব্রাউজার, প্রক্সি, লগ ফাইল, অ্যানালিটিক্স স্ক্রিপ্ট — সবাই প্রতিটি ক্লেইম পড়তে পারে। পেলোডে NID নম্বর, ফোন নম্বর, ভেতরের প্রাইসিং ফ্ল্যাগ, এমনকি পাসওয়ার্ড হ্যাশও আমরা প্রায়ই দেখি।

সমাধান: পেলোডে শুধু ততটুকুই রাখুন যা দিয়ে গ্রহণকারী API সিদ্ধান্ত নেবে: ইউজার আইডি, role বা scope, মেয়াদ। বাকি সব সার্ভারে খুঁজে নিন। টোকেনে সত্যিই গোপন তথ্য পাঠাতে হলে সাধারণ সাইন করা JWT-র বদলে এনক্রিপ্টেড JWE ব্যবহার করুন।

৬. দীর্ঘমেয়াদি টোকেন, বাতিলের কোনো উপায় নেই

JWT exp পর্যন্ত বৈধ থাকে — ইউজার লগআউট করলেও, পাসওয়ার্ড বদলালেও বা ব্যান হলেও, কারণ সার্ভার কিছু খুঁজে দেখে না। তাই ৩০ দিনের access token ফাঁস হলে সেটা ৩০ দিনের মাস্টার-চাবি।

সমাধান: access token ছোট রাখুন (সাধারণত ৫–১৫ মিনিট), সাথে একটা refresh token দিন যা সার্ভারে সংরক্ষিত থাকে, প্রতিবার ব্যবহারে বদলায় (rotate) এবং লগআউটে বাতিল হয়। আগেই বদলে যাওয়া refresh token আবার ব্যবহার হলে সেটা চুরির জোরালো লক্ষণ — তখন পুরো ফ্যামিলি বাতিল করুন। access token তাৎক্ষণিক বাতিল করতে চাইলে মেয়াদ শেষ হওয়া পর্যন্ত jti-এর একটা ছোট deny-list বা প্রতি ইউজারের “token version” রাখুন।

৭. এমন জায়গায় টোকেন রাখা যেখান থেকে XSS পড়তে পারে

localStorage বা sessionStorage-এর টোকেন পেজের যেকোনো JavaScript পড়তে পারে। একটা cross-site scripting বাগ, বা একটা আক্রান্ত npm প্যাকেজ বা থার্ড-পার্টি স্ক্রিপ্ট টোকেনটা অ্যাটাকারের সার্ভারে পাঠিয়ে দিতে পারে, আর মেয়াদ শেষ না হওয়া পর্যন্ত সেটা কাজ করবে।

HttpOnly কুকি JavaScript একদমই পড়তে পারে না:

Set-Cookie: session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=900

তবে এটা বিনা মূল্যের জয় নয় — ট্রেড-অফটা সৎভাবে বলা দরকার:

localStorage + হেডারHttpOnly কুকি
XSS টোকেন চুরি করতে পারেহ্যাঁনা (তবে পেজ খোলা থাকা পর্যন্ত XSS ইউজারের হয়ে রিকোয়েস্ট পাঠাতে পারে)
CSRF ঝুঁকিনেই — ব্রাউজার নিজে থেকে এটা জুড়ে দেয় নাআছে — ব্রাউজার নিজে থেকেই পাঠায়; SameSite আর state বদলানো রিকোয়েস্টে CSRF token দিয়ে ঠেকান
ভিন্ন ডোমেইনে কাজ করাসহজCORS আর কুকি সেটিং সাবধানে করতে হয়

সমাধান: ব্রাউজার অ্যাপে HttpOnly; Secure; SameSite কুকি বেছে নিন (অথবা এমন backend-for-frontend, যেখানে টোকেন পুরোপুরি সার্ভারেই থাকে), CSRF সুরক্ষা যোগ করুন, আর যেকোনো ক্ষেত্রেই আসল প্রতিরক্ষা হিসেবে XSS ঠেকানোর দিকে নজর দিন — আউটপুট এসকেপিং আর Content Security Policy।

৮. প্রোডাকশন টোকেন এমন অনলাইন টুলে পেস্ট করা যা আপলোড করে

চালু access token একটা ক্রেডেনশিয়াল। অনেক “JWT decoder” ওয়েবসাইট আপনার পেস্ট করা লেখা তাদের সার্ভারে পাঠায়, যেখানে সেটা লগ, ক্যাশ বা বিশ্লেষণ হতে পারে। টোকেনের মেয়াদ শেষ না হলে, ওই লগ যে পড়বে সে-ই ওই ইউজারের হয়ে আপনার API কল করতে পারবে।

সমাধান: সম্ভব হলে টেস্ট টোকেন দিয়ে ডিবাগ করুন; এমন টুল ব্যবহার করুন যা পুরোপুরি ব্রাউজারে চলে (ব্রাউজারের Network ট্যাবে দেখে নিশ্চিত হতে পারেন যে কিছু পাঠানো হচ্ছে না); আর আসল টোকেন ফাঁস হলে “কেউ দেখেনি” ধরে না নিয়ে সেশন বাতিল করুন বা মেয়াদ শেষ হওয়া পর্যন্ত অপেক্ষা করুন।

মনে রাখার নিয়ম: অ্যালগরিদম, কী আর প্রত্যাশিত ক্লেইম ঠিক করবে ভেরিফায়ার। টোকেন শুধু ডেটা নিয়ে আসে, যা ওই প্রত্যাশার সাথে মিলিয়ে দেখা হবে।

টোকেন ফাঁস না করেই পরীক্ষা করুন। JWT ডিকোডার প্রতিটি ক্লেইম দেখায়, মেয়াদোত্তীর্ণ বা none টোকেন নিয়ে সতর্ক করে আর Web Crypto দিয়ে স্থানীয়ভাবে সিগনেচার যাচাই করে — কিছুই আপলোড হয় না। এখনই চেষ্টা করুন

প্রশ্নোত্তর

প্রচলিত সেশনের চেয়ে JWT কি কম নিরাপদ?

স্বভাবগতভাবে নয়। সার্ভার-সাইড সেশন বাতিল করা সহজ আর ভুল কনফিগার করা কঠিন, তাই একটা মাত্র ওয়েব অ্যাপের জন্য প্রায়ই সেটাই ভালো ডিফল্ট। JWT কাজে লাগে যখন শেয়ার্ড সেশন স্টোর ছাড়াই একাধিক সার্ভিসকে পরিচয় যাচাই করতে হয়। যেকোনো ক্ষেত্রেই পার্থক্য গড়ে দেয় ওপরের ভুলগুলো।

HS256 কি অনিরাপদ? সবসময় কি RS256 ব্যবহার করব?

লম্বা র‍্যান্ডম সিক্রেটসহ HS256 নিরাপদ। এর সীমাবদ্ধতা হলো যে যাচাই করতে পারে সে সাইনও করতে পারে। যাচাইকারী আলাদা সার্ভিস বা থার্ড পার্টি হলে RS256 বা ES256 ব্যবহার করুন; ES256-এর সিগনেচার অনেক ছোট।

HttpOnly কি XSS থেকে পুরোপুরি বাঁচায়?

না। এটা স্ক্রিপ্টকে টোকেন পড়তে দেয় না, কিন্তু আপনার পেজে চলা স্ক্রিপ্ট এমন রিকোয়েস্ট পাঠাতে পারে যেটা ব্রাউজার কুকি দিয়ে অথেন্টিকেট করবে। এতে ক্ষতি পেজ খোলা থাকার সময়ে সীমিত থাকে; XSS ঠিক করার বিকল্প এটা নয়।

টোকেন ফাঁস হলে কী করব?

সংশ্লিষ্ট সেশন বা refresh token বাতিল করুন, deny-list থাকলে jti যোগ করুন, আর সাইন করার সিক্রেটই ফাঁস হয়ে থাকতে পারলে সেটা বদলে ফেলুন — এতে ওই সিক্রেট দিয়ে সাইন করা সব টোকেন অবৈধ হয়ে যাবে।
