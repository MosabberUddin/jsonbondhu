JSON vs YAML vs XML: which one should you use?

Your API returns JSON, your Docker Compose and CI files are YAML, and the bank or government system you have to integrate with still speaks XML. All three formats store the same kind of thing — structured data — but they were designed for different jobs, and each has traps that only show up in production. This guide puts the same data side by side, compares them honestly, and gives you a simple rule for choosing.

The same data in three formats

Here is a small service configuration: a name, a port, a flag, a country code, a version, a list of admins and a nested database block.

JSON

{
  "service": "checkout",
  "port": 8080,
  "debug": false,
  "country": "NO",
  "version": "3.10",
  "admins": ["rahim@example.com", "karim@example.com"],
  "database": { "host": "db.internal", "pool": 10 }
}

YAML

# Checkout service settings
service: checkout
port: 8080
debug: false
country: "NO"       # quoted on purpose, see below
version: "3.10"
admins:
  - rahim@example.com
  - karim@example.com
database:
  host: db.internal
  pool: 10

XML

<?xml version="1.0" encoding="UTF-8"?>
<!-- Checkout service settings -->
<service name="checkout">
  <port>8080</port>
  <debug>false</debug>
  <country>NO</country>
  <version>3.10</version>
  <admins>
    <admin>rahim@example.com</admin>
    <admin>karim@example.com</admin>
  </admins>
  <database host="db.internal" pool="10"/>
</service>

Three things stand out. YAML is the shortest and allows comments. JSON is compact and unambiguous. XML is the most verbose, but it has two ways to hold data — child elements and attributes (name="checkout") — and in XML every value is just text: 8080 and false are strings unless a schema says otherwise.

JSON: the default for data exchange

JSON’s strength is that it is boring. There is exactly one way to write a string, a number or a boolean, so two programs in different languages always agree on what the data means. JSON.parse is built into every browser, and parsing is fast. The price is that it is unpleasant to hand-edit: no comments, no trailing commas, and every key needs quotes. That is why it is ideal between programs and less ideal for files people maintain by hand.

YAML: friendly, but with sharp edges

YAML was designed for humans: indentation instead of brackets, comments, multi-line strings, and anchors (&/*) to reuse blocks. YAML 1.2 is (almost) a superset of JSON, so most valid JSON is also valid YAML. But the friendliness comes from guessing, and guessing goes wrong:

The Norway problem. In YAML 1.1, unquoted yes, no, on, off (in several capitalisations) are booleans. So country: NO becomes country: false. YAML 1.2 fixed this, but popular parsers such as Python’s PyYAML still follow 1.1. Quote any value that could be mistaken for something else.

  • Numbers that aren’t numbers. version: 3.10 is read as the float 3.1. Version strings, postcodes and phone numbers need quotes.
  • Indentation is the structure. Tabs are not allowed for indentation, and moving a line two spaces left silently moves it to a different parent. A diff that looks like a whitespace change can change meaning.
  • Many ways to say the same thing. Strings can be plain, single-quoted, double-quoted, | literal or > folded, each with its own escaping and newline rules.
  • Unsafe loading. Some YAML loaders can create arbitrary objects from tags. In Python always use yaml.safe_load() for untrusted input.

XML: verbose, but built for documents

XML predates JSON and was designed for marked-up documents as much as for data. It supports mixed content (text with tags inside it, like HTML), namespaces for combining vocabularies, and the most powerful schema and transformation tools of the three: XSD for validation, XPath for querying and XSLT for transforming. That is why formats such as SVG, RSS, DOCX/XLSX internals and many financial and government interfaces are XML. The costs are size, verbosity and a design choice with no single right answer — element or attribute? For new web APIs, XML is rarely chosen today; for integrating with systems that already use it, you simply follow their schema.

Security note: an XML parser that resolves external entities can be tricked into reading local files (an “XXE” attack). When parsing XML from outside, make sure DTD and external entity processing is disabled in your library.

How to choose

  • Programs talking to programs (APIs, messages, storage): JSON.
  • Config files that people edit and review: YAML if the ecosystem expects it (Kubernetes, CI); otherwise JSON, or a JSON-with-comments variant your tool supports. Keep YAML flat and quote anything ambiguous.
  • Documents, or a partner who requires it: XML, validated against their XSD.

You don’t have to commit forever. Because all three describe trees of values, converting between them is mechanical — just check that nothing was re-typed along the way.

FAQ

Is YAML a superset of JSON?

Since YAML 1.2, practically yes: a JSON document can be loaded by a YAML 1.2 parser. The reverse is not true — comments, anchors and unquoted strings are not JSON.

Is JSON faster than XML?

Usually JSON is smaller on the wire and quicker to parse, especially in browsers where the parser is built in. For most apps the difference matters far less than network time, so choose by fit, not speed.

Why did my YAML value turn into true or a different number?

YAML guesses types for unquoted values. Words like no or on can become booleans in YAML 1.1 parsers, and 3.10 becomes 3.1. Put such values in quotes.

Can I validate YAML with JSON Schema?

Yes, this is common. Load the YAML into data, then validate that data with a JSON Schema validator; many editors do this for Kubernetes and CI files.

JSON, YAML না XML: কোনটি ব্যবহার করবেন?

আপনার API ফেরত দেয় JSON, Docker Compose আর CI ফাইলগুলো YAML-এ, আর যে ব্যাংক বা সরকারি সিস্টেমের সাথে ইন্টিগ্রেশন করতে হবে, সেটা এখনো XML-এ কথা বলে। তিনটি ফরম্যাটই একই ধরনের জিনিস রাখে — গোছানো ডেটা — কিন্তু তৈরি হয়েছে আলাদা আলাদা কাজের জন্য, আর প্রতিটিরই এমন কিছু ফাঁদ আছে যা ধরা পড়ে একেবারে প্রোডাকশনে গিয়ে। এই গাইডে একই ডেটা পাশাপাশি রেখে তিনটির সৎ তুলনা করা হয়েছে, আর বেছে নেওয়ার একটা সহজ নিয়মও দেওয়া হয়েছে।

একই ডেটা তিন ফরম্যাটে

নিচে একটি ছোট সার্ভিস কনফিগারেশন: একটি নাম, পোর্ট, একটি ফ্ল্যাগ, দেশের কোড, ভার্সন, অ্যাডমিনদের তালিকা আর নেস্টেড একটি ডেটাবেস ব্লক।

JSON

{
  "service": "checkout",
  "port": 8080,
  "debug": false,
  "country": "NO",
  "version": "3.10",
  "admins": ["rahim@example.com", "karim@example.com"],
  "database": { "host": "db.internal", "pool": 10 }
}

YAML

# Checkout সার্ভিসের সেটিংস
service: checkout
port: 8080
debug: false
country: "NO"       # ইচ্ছা করেই কোটে রাখা, নিচে দেখুন
version: "3.10"
admins:
  - rahim@example.com
  - karim@example.com
database:
  host: db.internal
  pool: 10

XML

<?xml version="1.0" encoding="UTF-8"?>
<!-- Checkout সার্ভিসের সেটিংস -->
<service name="checkout">
  <port>8080</port>
  <debug>false</debug>
  <country>NO</country>
  <version>3.10</version>
  <admins>
    <admin>rahim@example.com</admin>
    <admin>karim@example.com</admin>
  </admins>
  <database host="db.internal" pool="10"/>
</service>

তিনটি জিনিস চোখে পড়ে। YAML সবচেয়ে ছোট আর কমেন্ট লেখা যায়। JSON সংক্ষিপ্ত আর দ্ব্যর্থহীন। XML সবচেয়ে লম্বা, আর এতে ডেটা রাখার দুটি উপায় আছে — চাইল্ড এলিমেন্ট আর অ্যাট্রিবিউট (name="checkout")। তা ছাড়া XML-এ প্রতিটি মানই আসলে লেখা: স্কিমা আলাদা করে না বললে 8080 আর false দুটোই স্ট্রিং।

JSON: ডেটা আদান-প্রদানের ডিফল্ট

JSON-এর শক্তি হলো এটা একঘেয়ে। একটি স্ট্রিং, সংখ্যা বা boolean লেখার ঠিক একটাই উপায়, তাই আলাদা ভাষায় লেখা দুটি প্রোগ্রাম ডেটার মানে নিয়ে সবসময় একমত হয়। JSON.parse প্রতিটি ব্রাউজারে বিল্ট-ইন, আর পার্সিংও দ্রুত। বিনিময়ে হাতে এডিট করা ঝামেলার: কমেন্ট নেই, শেষে কমা দেওয়া যায় না, প্রতিটি কী-তে কোট লাগে। তাই প্রোগ্রামে-প্রোগ্রামে কথাবার্তার জন্য JSON আদর্শ, কিন্তু মানুষ হাতে যে ফাইল রক্ষণাবেক্ষণ করে, তার জন্য ততটা নয়।

YAML: বন্ধুসুলভ, কিন্তু ধারালো কিনারা আছে

YAML বানানো হয়েছে মানুষের কথা ভেবে: ব্র্যাকেটের বদলে ইনডেন্টেশন, কমেন্ট, একাধিক লাইনের স্ট্রিং, আর ব্লক পুনর্ব্যবহারের জন্য অ্যাংকর (&/*)। YAML 1.2 (প্রায়) JSON-এর সুপারসেট, তাই বেশিরভাগ বৈধ JSON বৈধ YAML-ও। কিন্তু এই বন্ধুত্বপূর্ণ ভাব আসে অনুমান থেকে, আর অনুমান ভুলও হয়:

নরওয়ে সমস্যা। YAML 1.1-এ কোট ছাড়া yes, no, on, off (বিভিন্ন ছোট-বড় হাতের রূপে) boolean হিসেবে পড়া হয়। ফলে country: NO হয়ে যায় country: false। YAML 1.2 এটা ঠিক করেছে, কিন্তু Python-এর PyYAML-এর মতো জনপ্রিয় পার্সার এখনো 1.1 মেনে চলে। অন্য কিছু বলে ভুল হতে পারে এমন যেকোনো মান কোটে রাখুন।

  • যে সংখ্যা আসলে সংখ্যা নয়। version: 3.10 পড়া হয় float 3.1 হিসেবে। ভার্সন, পোস্টকোড, ফোন নম্বর — এসব কোটে রাখতে হবে।
  • ইনডেন্টেশনই কাঠামো। ইনডেন্টেশনে ট্যাব চলে না, আর একটি লাইন দুই স্পেস বাঁয়ে সরালে সেটা নিঃশব্দে অন্য প্যারেন্টের অধীনে চলে যায়। যে diff দেখতে শুধু স্পেসের পরিবর্তন, সেটাও মানে বদলে দিতে পারে।
  • একই কথা বলার অনেক উপায়। স্ট্রিং হতে পারে প্লেইন, সিঙ্গেল-কোটেড, ডাবল-কোটেড, | literal বা > folded — প্রতিটির এসকেপিং আর নিউলাইনের নিয়ম আলাদা।
  • অনিরাপদ লোডিং। কিছু YAML লোডার ট্যাগ দেখে যেকোনো অবজেক্ট তৈরি করে ফেলতে পারে। Python-এ অবিশ্বস্ত ইনপুটের জন্য সবসময় yaml.safe_load() ব্যবহার করুন।

XML: লম্বা, কিন্তু ডকুমেন্টের জন্য তৈরি

XML এসেছে JSON-এর আগে, আর এটা ডেটার পাশাপাশি মার্কআপ করা ডকুমেন্টের কথা ভেবেও বানানো। এতে mixed content (HTML-এর মতো লেখার ভেতরে ট্যাগ), আলাদা ভোকাবুলারি একসাথে মেশানোর জন্য namespace, আর তিনটির মধ্যে সবচেয়ে শক্তিশালী স্কিমা ও রূপান্তরের টুল আছে: যাচাইয়ের জন্য XSD, খোঁজার জন্য XPath, রূপান্তরের জন্য XSLT। এ কারণেই SVG, RSS, DOCX/XLSX-এর ভেতরের ফাইল আর অনেক আর্থিক ও সরকারি ইন্টারফেস XML-এ। খরচ হলো আকার, বাড়তি শব্দ, আর এমন একটা সিদ্ধান্ত যার কোনো একক সঠিক উত্তর নেই — এলিমেন্ট না অ্যাট্রিবিউট? নতুন ওয়েব API-এর জন্য এখন XML কমই বেছে নেওয়া হয়; যে সিস্টেম আগে থেকেই XML ব্যবহার করে, তার সাথে কাজ করলে শুধু তাদের স্কিমা মেনে চলুন।

নিরাপত্তা নোট: যে XML পার্সার external entity রিজলভ করে, তাকে দিয়ে কৌশলে সার্ভারের লোকাল ফাইল পড়িয়ে নেওয়া যায় (“XXE” অ্যাটাক)। বাইরে থেকে আসা XML পার্স করার সময় নিশ্চিত করুন আপনার লাইব্রেরিতে DTD আর external entity প্রসেসিং বন্ধ আছে।

কীভাবে বেছে নেবেন

  • প্রোগ্রামের সাথে প্রোগ্রামের কথা (API, মেসেজ, স্টোরেজ): JSON।
  • যে কনফিগ ফাইল মানুষ এডিট ও রিভিউ করে: ইকোসিস্টেম YAML চাইলে (Kubernetes, CI) YAML; নইলে JSON, অথবা আপনার টুল সমর্থন করলে কমেন্টসহ JSON-এর কোনো রূপ। YAML যতটা সম্ভব সমতল রাখুন আর দ্ব্যর্থক সবকিছু কোটে দিন।
  • ডকুমেন্ট, অথবা পার্টনার যদি দাবি করে: XML, তাদের XSD দিয়ে যাচাই করে।

চিরকালের জন্য বাঁধা পড়ার দরকার নেই। তিনটিই যেহেতু মানের ট্রি বর্ণনা করে, একটি থেকে আরেকটিতে রূপান্তর যান্ত্রিক কাজ — শুধু দেখে নিন পথে কোনো মানের টাইপ বদলে গেল কি না।

JSON থেকে YAML বা XML-এ রূপান্তর করুন। ফরম্যাটারে JSON পেস্ট করে Convert ট্যাব খুলুন আর YAML বা XML বেছে নিন — "NO"-এর মতো দ্ব্যর্থক মান নিজে থেকেই কোটে রাখা হয়। এখনই চেষ্টা করুন

প্রশ্নোত্তর

YAML কি JSON-এর সুপারসেট?

YAML 1.2 থেকে কার্যত হ্যাঁ: একটি JSON ডকুমেন্ট YAML 1.2 পার্সার দিয়ে লোড করা যায়। উল্টোটা সত্য নয় — কমেন্ট, অ্যাংকর আর কোট ছাড়া স্ট্রিং JSON নয়।

JSON কি XML-এর চেয়ে দ্রুত?

সাধারণত JSON নেটওয়ার্কে আকারে ছোট আর পার্স করতে দ্রুত, বিশেষ করে ব্রাউজারে, যেখানে পার্সার বিল্ট-ইন। তবে বেশিরভাগ অ্যাপে এই পার্থক্যের চেয়ে নেটওয়ার্কের সময় অনেক বেশি গুরুত্বপূর্ণ, তাই গতি নয়, কাজের সাথে মিল দেখে বেছে নিন।

আমার YAML-এর মান কেন true বা অন্য সংখ্যা হয়ে গেল?

কোট ছাড়া মানের টাইপ YAML অনুমান করে। YAML 1.1 পার্সারে no বা on-এর মতো শব্দ boolean হয়ে যেতে পারে, আর 3.10 হয়ে যায় 3.1। এমন মান কোটে রাখুন।

YAML কি JSON Schema দিয়ে যাচাই করা যায়?

হ্যাঁ, এটা বেশ প্রচলিত। YAML লোড করে ডেটায় রূপান্তর করুন, তারপর সেই ডেটা JSON Schema ভ্যালিডেটর দিয়ে যাচাই করুন; অনেক এডিটর Kubernetes আর CI ফাইলের জন্য এটা নিজেই করে।
